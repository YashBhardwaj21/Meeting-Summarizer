# Development

## Local Environment

You need:
* Docker + Docker Compose
* Ollama running on the host (see the main [README](../README.md) for model pull commands)
* Node.js (matching the `frontend/Dockerfile` base, `node:20`) if running the frontend outside Docker
* Python 3.11 if running the backend outside Docker (matches `backend/Dockerfile`)

## Running the Stack

```bash
docker compose up --build
```
This builds and starts `frontend`, `backend`, `worker`, `db`, `redis`, and `minio`. The backend and worker containers both build from `backend/Dockerfile` but run different commands (see below).

Rebuild a single service after changing its Dockerfile or dependencies:
```bash
docker compose up --build backend
docker compose up --build worker
docker compose up --build frontend
```

## Backend Development

The backend container's entrypoint (`backend-entrypoint.sh`) runs `alembic upgrade head` before starting Uvicorn — migrations apply automatically on every backend container start.

Container command:
```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

The Dockerfile runs without hot-reload for stability. For active backend development with auto-reload, run it outside Docker against the Compose-provided Postgres/Redis/MinIO:

```bash
cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

> [!NOTE]
> Point `DATABASE_URL`, `REDIS_URL`, and the storage endpoints at `localhost` (the Compose-exposed ports) rather than the internal service names (`db`, `redis`, `minio`) when running this way.

Source is bind-mounted (`./backend:/app`) in Compose, so most Python changes are picked up without a rebuild — only dependency or Dockerfile changes require `--build`.

## Frontend Development

For hot-reload during UI work, run Vite directly instead of the Nginx-based Docker build:

```bash
cd frontend
npm install
npm run dev
```

Set `VITE_API_BASE_URL` in `frontend/.env` (see `frontend/.env.example`) to point at the backend, e.g. `http://localhost:8000/api/v1`.

Other scripts:
```bash
npm run build    # type-check (tsc -b) and production build
npm run lint     # eslint
npm run preview  # preview the production build locally
```

The Docker image itself builds via a two-stage Dockerfile: Vite build in a Node stage, served by Nginx in the final image, with `VITE_API_BASE_URL` baked in at build time as a build arg.

## Worker Development

The worker runs the same backend image but with a different command:
```bash
arq app.workers.worker.WorkerSettings
```

> [!IMPORTANT]
> Unlike the backend service, the worker container does not run the entrypoint script — it does not run migrations itself. Migrations are only applied by the backend service on startup, so backend should come up (or have already come up) before relying on schema changes in the worker.

To iterate on pipeline code (`app/workers/`, `app/services/transcription_service.py`, `app/integrations/`), restart just the worker:
```bash
docker compose restart worker
```
Source is bind-mounted, so restarting is enough for Python changes — no rebuild needed unless dependencies changed.

## Database Migrations

Migrations are managed with Alembic (`backend/alembic/`).

Generate a new migration after changing SQLAlchemy models:
```bash
cd backend
alembic revision --autogenerate -m "describe the change"
```

Apply migrations manually (normally handled automatically by the backend entrypoint):
```bash
alembic upgrade head
```

> [!WARNING]
> Review the autogenerated migration before committing — `autogenerate` does not reliably detect every schema change (e.g. some index or constraint changes).

## Tests

Backend tests use `pytest` with `pytest-asyncio`:
```bash
cd backend
pytest
```

Test files cover unit tests (chunking, transcription logic), service-level tests (meetings, files, chats), and integration tests (`test_integration_upload.py`, `test_integration_worker.py`) against the real pipeline path.

There is no frontend test runner configured in `package.json` yet, despite a test file existing under `src/components/meetings/__tests__/`; wire up a runner (e.g. Vitest) before relying on it.

## Logs

```bash
docker compose logs -f          # all services
docker compose logs -f worker   # pipeline processing
docker compose logs -f backend  # API requests
```

Job-level pipeline stages and timings are also logged from `app/workers/transcription.py` (`[PIPELINE] ...` lines) and stored per-job in `ProcessingJob` metrics — check the `/jobs` endpoints before digging through logs for a specific meeting's failure.

## Rebuilding Containers

```bash
docker compose down             # stop, keep volumes (data persists)
docker compose down -v          # stop and wipe volumes (fresh DB/storage)
docker compose up --build       # rebuild all images and start
```

Use `down -v` when you need a clean Postgres/MinIO state, e.g. after a broken migration during development.
